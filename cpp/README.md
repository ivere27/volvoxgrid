# C++ binding (header-only)

Header-only C++ binding for the VolvoxGrid native runtime, usable from any
Windows or POSIX host: **ATL, WTL, MFC, raw Win32, Qt, GTK, Linux desktop,
macOS, FreeBSD**. No COM, no libprotobuf, no gRPC — just `LoadLibrary`/`dlopen`
+ typed RAII over the existing `Synurang_*` FFI exports.

Compiles cleanly at `-std=c++11`, `c++14`, and `c++17`.

If you want a COM/ActiveX control instead, see [`adapters/vsflexgrid`](../adapters/vsflexgrid).

## Two ways to use it

You pick how much of the stack you want to pull in. The layers are additive —
each header builds on the one(s) above it, and you stop wherever your host's
needs are met.

| Layer | Header(s) | Use when |
| --- | --- | --- |
| **1. Raw FFI (single header)** | `volvoxgrid.hpp` | You already serialize protobufs yourself, or your host calls the C ABI directly (MFC/ATL hosts, custom transports). |
| **2. Typed messages + lite client** | `volvoxgrid.hpp` + `synurang_lite.hpp` + `volvoxgrid_lite_transport.hpp` + `generated/volvoxgrid_lite.hpp` | You want struct-based request/response messages and a typed `VolvoxGridServiceLite` client with no libprotobuf dependency. |

Both layers are header-only — zero `.cpp` files to compile, zero libraries to
link. The runtime itself (`libvolvoxgrid.so`/`.dll`/`.dylib`) is loaded
dynamically at process start.

## Layout

```
cpp/
├── include/
│   ├── volvoxgrid.hpp                   # Layer 1 — dlopen + C ABI wrapper
│   ├── synurang_lite.hpp                # Layer 2 — varint codec, Optional<T>, Transport
│   ├── volvoxgrid_lite_transport.hpp    # Layer 2 — bridge Runtime → Transport
│   └── generated/
│       └── volvoxgrid_lite.hpp          # Layer 2 — generated message structs + client
├── examples/
│   ├── tui/                             # Layer 1 — ASCII-table demo (3x3 string round-trip)
│   └── gtk/                             # Layer 2 — GTK4 window with typed RenderSession
└── README.md
```

## Layer 1 — raw FFI (single header)

```cpp
#include "volvoxgrid.hpp"

volvoxgrid::Runtime rt("volvoxgrid.dll");   // .so on Linux, .dylib on macOS
rt.init();

if (rt.has_gpu_renderer()) { /* full build with wgpu */ }

// Unary RPC: method path + protobuf-encoded request bytes -> response bytes.
std::vector<uint8_t> resp = rt.invoke("/volvoxgrid.v1.VolvoxGridService/Create", create_req_bytes);

// Bidirectional streaming (used for the RenderSession render loop).
auto stream = rt.open_stream("/volvoxgrid.v1.VolvoxGridService/RenderSession");
stream.send(request_bytes);
auto reply = stream.recv();          // {data, status}; status==1 means EOF
stream.close_send();
```

The header maps directly onto these exports (see `dist/ios/volvoxgrid.h`):

| Header API | DLL export |
| --- | --- |
| `Runtime::init()` | `VolvoxGrid_Init` |
| `Runtime::invoke(method, payload)` | `Synurang_Invoke_VolvoxGridService` |
| `Runtime::open_stream(method)` | `Synurang_Stream_VolvoxGridService_Open` |
| `Stream::send`, `recv`, `close_send`, `close` | `Synurang_Stream_*` |
| `Runtime::has_builtin_text_engine()` | `volvox_grid_has_builtin_text_engine` |
| `Runtime::has_gpu_renderer()` | `volvox_grid_has_gpu_renderer` |

## Layer 2 — typed messages + lite client

Adds three more headers — all still header-only, all still zero-dep:

- **`synurang_lite.hpp`** — vendored shared runtime: protobuf varint/fixed
  reader+writer, `Optional<T>` (aliases `std::optional` on C++17, polyfill on
  C++11/14), Well-Known Type shims (`Empty`, `Timestamp`, wrapper types), and
  the abstract `Transport` / `Stream` interfaces the generated client calls.
- **`volvoxgrid_lite_transport.hpp`** — 75-line adapter that exposes
  `volvoxgrid::Runtime` as a `synurang::lite::Transport`. Replace this with
  your own implementation if you wire the messages over a different transport.
- **`generated/volvoxgrid_lite.hpp`** — generated by `protoc-gen-synurang-ffi`
  from `proto/volvoxgrid.proto`. One struct per message, one `*Lite` class per
  service. Regenerate with `make codegen` at the repo root.

```cpp
#include "volvoxgrid.hpp"
#include "volvoxgrid_lite_transport.hpp"
#include "generated/volvoxgrid_lite.hpp"

namespace vg = volvoxgrid::v1;

volvoxgrid::Runtime rt("volvoxgrid.dll");
rt.init();

volvoxgrid::lite_transport::RuntimeTransport transport(&rt);
vg::VolvoxGridServiceLite client(&transport);

// Unary — typed in, typed out, wire format is internal.
vg::CreateRequest req;
req.viewport_width = 800;
req.viewport_height = 500;
req.scale = 1.0f;
auto resp = client.Create(req);
int64_t grid_id = resp.grid_id;

// Bidi streaming — RenderSession render loop.
auto session = client.RenderSession();
vg::RenderInput in;
in.grid_id = grid_id;
in.viewport = std::make_shared<vg::ViewportState>();
in.viewport->width  = 800;
in.viewport->height = 500;
in.input_case = vg::RenderInput::InputCase::kViewport;
session.send(in);

vg::RenderOutput out;
while (session.recv(out)) {
    if (out.event_case == vg::RenderOutput::EventCase::kFrameDone) { /* present */ break; }
}
session.close_send();
```

**Cost on this proto** (284 messages, 19,460 lines of generated header):
single-TU compile is 6–8 s at `-O0`/`-O2`. Optimised binaries are ~250 KB
(linker drops every unused message via `-Wl,--gc-sections`). Bigger
header-only libraries exist; this is in the "don't think about it" zone.

**Using a non-volvoxgrid transport.** Implement `synurang::lite::Transport`
(in `synurang_lite.hpp`) for whatever runtime you have — HTTP, named pipes,
shared memory — and the same generated `*Lite` clients work unchanged. The
`volvoxgrid_lite_transport.hpp` adapter is itself only 75 lines; use it as
the reference implementation.

## Build the examples

### `examples/tui/` — Layer 1 (raw FFI, engine TUI renderer)

Uses `volvoxgrid.hpp` alone; `-std=c++11` is enough. Defines six columns
(`name`, `sales`, `region`, `active`, `score`, `updated`) and twelve rows
of demo data, then drives the built-in `RENDERER_TUI` renderer over a bidi
`RenderSession` stream. The engine writes ANSI escape bytes into a buffer
we hand it via `BufferReady.handle`; we just `fwrite` the result. Arrow
keys are forwarded to the engine via `TerminalInputBytes` to move the
selection; `q` or `Ctrl+C` quits. All wire-format encoding uses
`volvoxgrid::pb::` from the single header — no codegen, no libprotobuf.

```bash
cd cpp/examples/tui
g++ -std=c++11 -I../../include main.cpp -ldl -o vg_tui
curl -L -o /tmp/volvoxgrid-desktop.jar \
    https://github.com/ivere27/volvoxgrid/releases/download/v0.8.10/volvoxgrid-desktop-0.8.10.jar
unzip -p /tmp/volvoxgrid-desktop.jar \
    native/linux-x86_64/libvolvoxgrid.so > /tmp/libvolvoxgrid.so
./vg_tui /tmp/libvolvoxgrid.so
# (engine takes over the alt-screen and renders a colorized box-drawn table)
#   ║name      │sales     │region    │active    │score     │updated
#  1║Alpha     │1200      │EMEA      │true      │4.7       │2026-04-12
#  2║Beta      │950       │APAC      │false     │3.9       │2026-04-08
#  3║Gamma     │1875      │NA        │true      │4.2       │2026-04-19
# ... (12 rows total)
# Arrows: move  q: quit
```

Or via CMake:

```bash
cmake -S . -B build && cmake --build build && ./build/vg_tui /tmp/libvolvoxgrid.so
```

**Windows / MinGW or MSVC:** same recipe with `x86_64-w64-mingw32-g++` or
`cl /std:c++11 /EHsc`; copy `volvoxgrid.dll` next to the resulting `.exe`.

### `examples/gtk/` — Layer 2 (typed messages + streaming)

A small GTK4 C++ app that loads the runtime, renders the "sales" demo grid
to a Cairo-backed buffer, and handles scroll/resize. Uses all four headers
from Layer 2 above — messages are typed structs and there's zero hand-rolled
protobuf wire-format code in `main.cpp`.

```bash
cd cpp/examples/gtk
cmake -S . -B build && cmake --build build
VOLVOXGRID_LIBRARY=/tmp/libvolvoxgrid.so ./build/vg_gtk
```

To regenerate `volvoxgrid_lite.hpp` from `proto/volvoxgrid.proto`, run
`make codegen` at the repo root.

## ATL/WTL host sketch

ATL doesn't need a special adapter — it just hosts the C ABI directly:

```cpp
class CMainDlg : public CDialogImpl<CMainDlg> {
    volvoxgrid::Runtime rt_{"volvoxgrid.dll"};
    LRESULT OnInitDialog(UINT, WPARAM, LPARAM, BOOL&) {
        rt_.init();
        // ... build your own HWND host using the streaming surface
        return TRUE;
    }
};
```

If you want a drop-in HWND-hosted control instead of writing your own host,
embed the ActiveX OCX with `CAxWindow` — that's what ATL was built for and
needs zero new C++ on this side.
